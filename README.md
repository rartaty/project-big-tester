# Project Big Tester

## 概要

Project Big Tester は、資産管理と運用の支援・自動化を目的に開発している**個人向け資産管理・運用アプリケーション**です。保有情報や資産推移の確認、市場・企業情報の分析、短期・長期・シーン別の運用検討、仮想取引による検証、レポート作成を扱い、判断材料と処理の経緯を確認できるようにしています。

※自動化には、情報取得・整理・定期処理・記録を含みます。実資金による自動売買の完成・稼働を示すものではありません。

本リポジトリには、実システムの概要と、実装から公開可能な部分を切り出したソースコードを掲載しています。独立した架空のアプリを再現したデモではありません。投資判断や外部接続を担う部分は含まないため、システム全体を起動する配布版ではありません。

### 主要な機能

| 領域 | 機能 |
| --- | --- |
| 資産情報の確認 | 保有情報、資産の推移、区分別の状態を画面で確認 |
| 市場・企業情報 | 外部データを取得し、分析や閲覧に使う情報を整理 |
| 投資分析 | 短期・長期・シーン別に処理を分け、目的に応じて分析・検証 |
| AI 支援 | Google Gemini / OpenAI GPT を利用した情報整理、定性的な分析、説明・レポート作成の補助 |
| 仮想取引・検証 | 実際の注文と区別した仮想取引、検証結果や処理履歴の記録 |
| 閲覧・運用確認 | ダッシュボード、分析、監視、レポート、タイムラインによる確認 |

### 銀行連携と投資区分

**銀行口座とは現在接続していません（2026-10-12 時点）。** 銀行関連の連携は残高照会などの閲覧に限定する設計で、送金・出金の操作は提供しません。システム全体には分析・記録・仮想取引の処理もあり、銀行機能の閲覧専用という性質とは区別しています。

投資分析の処理は、**短期・長期・市場の状況に応じたシーン別**の区分を持ちます。本リポジトリでは区分の存在と役割までを説明し、具体的な銘柄選定、売買条件、評価式、閾値、配分、切り替え条件は掲載していません。

## 技術スタック

以下は元システムの採用技術です。本リポジトリに実装全体や各製品の設定を収録しているという意味ではありません。

| 領域 | 技術 | 用途 |
| --- | --- | --- |
| Backend | Python / FastAPI / Pydantic | API、データの検証、処理の取りまとめ |
| データアクセス | SQLAlchemy | データベース操作 |
| スケジューリング | APScheduler | 時間に基づく処理の実行 |
| データ処理 | pandas | 取得した情報の整形・集計 |
| データ基盤 | PostgreSQL / TimescaleDB / Parquet | 業務データ、時系列データ、長期保存の役割分担 |
| Frontend | Next.js / React / TypeScript | ダッシュボードと閲覧画面 |
| 可視化 | Recharts | 時系列・集計情報のグラフ表示 |
| AI | Google Gemini / OpenAI GPT | 情報整理、分析支援、説明・レポート作成 |
| 外部連携 | 市場・企業データサービス / 通知サービス | 情報取得、状態通知 |
| シークレット管理 | AWS Systems Manager Parameter Store / KMS | 認証情報をソースコードから分離して管理 |

### 技術選定・設計の理由

| 対象 | 選定・設計方針 | 理由・トレードオフ |
| --- | --- | --- |
| アプリケーション構成 | UI、API、共通処理、データ管理の責務を分離 | 各領域の役割を明確にする方針。接続部分の整合を管理する必要がある。 |
| データ基盤 | 初期の SQLite から PostgreSQL / TimescaleDB を用いる構成へ変更し、長期保存に Parquet を利用 | 並行書き込み、時系列データの増加、JSONB 検索の要件に対応するため。単一ファイルの DB より構築・運用の負担は増える。 |
| AI の利用 | Gemini / GPT を処理の性質に応じて使い分ける | 品質・コスト・待ち時間の要求が異なるため。複数の処理経路を管理する必要がある。 |
| 認証情報 | Parameter Store Standard tier とアプリケーション側の検証・運用監査を組み合わせる | コストと運用負荷を考慮しながらソースコードへの秘密値の埋め込みを避けるため。認証情報の更新や監査は別途運用する。 |
| 外部通信・通知 | レート制限、タイムアウト、再試行制御、テスト時の通信抑止 | 呼び出し過多と外部障害の影響を制御し、テストを外部状態から隔離するため。待ち時間や失敗の扱いを明示する必要がある。 |
| コスト・監査 | 処理状態、抑止理由、コスト関連イベントを記録 | 意図しない実行やコスト増加を制御し、処理の経緯を確認するため。記録の保存範囲と機微情報の除外を管理する。 |

設計上の理由を確認できる項目のみを説明しています。すべてのライブラリーに、他製品との比較記録があるわけではありません。

## 環境構築と使い方

### 文書とコードを読む

GitHub 上で閲覧するか、Code → Download ZIP から取得して展開してください。[システム概要](docs/SYSTEM_OVERVIEW.md)から全体像を確認し、[コードの収録範囲](docs/CODE_SCOPE.md)を参照すると各ファイルの役割が分かります。

### 公開した Python コードの確認

Python 3.11 以降を用意し、リポジトリのルートで実行します。標準ライブラリーのみを使用し、DB・API キー・外部サービスの設定は不要です。

```sh
python -m unittest discover -s tests -p "test_*.py"
```

テストでは専用の一時的な環境変数を使用します。元システムの設定を読み込む必要はありません。

### Frontend コードの確認

`PositionsTable.tsx` は、渡された保有情報を表示する React / TypeScript の部品です。CSS Modules 対応環境と、同梱の型定義・共通スタイルを前提とします。データ取得や発注の処理は持ちません。

画面全体やアプリの起動設定は収録していません。本リポジトリ単独で Next.js のアプリを起動する手順は提供していません。

## セキュリティと運用ルール

### 本システムで重視する設計

認証情報の保護に加え、意図しない実行・外部通信・費用発生を抑え、処理の経緯を確認できることを重視しています。以下は設計資料と該当実装で確認した方針です。

| 観点 | 特徴・こだわり | 目的 |
| --- | --- | --- |
| 認証情報の管理 | Parameter Store / KMS を用い、秘密値をソースコードから分離 | コードの共有と認証情報の管理を切り分ける |
| サーバー側の認証 | 管理操作向けの認証処理をサーバー側に置き、本番向けの認証では必要な設定が欠けている場合に拒否する | 画面上の操作制限だけに依存せず、設定不足を許可扱いにしない |
| 停止と再開 | 停止状態を保存し、起動時の不整合では停止側を優先。解除処理には明示的な確認を要求 | 再起動や状態の不一致による不用意な処理再開を防ぐ |
| テストの隔離 | 隔離テストでは AI 呼び出しや通知送信を抑止し、検証用の応答を使用 | テストによる外部への送信、費用発生、実運用への影響を抑える |
| 外部サービスへの負荷 | レート制限、タイムアウト、回数などを制御した再試行を設ける | 呼び出し過多と外部障害の影響を抑える |
| 処理の追跡 | 実行・抑止・停止解除などの運用イベントを記録 | 処理が行われた理由や停止した経緯を確認できるようにする |

これらは元システムの設計・実装の説明です。本リポジトリには各対策の実装一式を収録していません。また、個別の仕組みの存在は、システム全体の安全性やすべての経路での適用を保証するものではありません。
